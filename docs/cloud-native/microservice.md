## 要点提纲

### 1. 拆分的粒度判断

- 组织维度（康威定律）：服务边界 ≈ 团队边界
- 业务维度：高内聚域优先；"一个需求改几个服务"是反向信号
- 经验法则：宁可先粗后细；拆分的成本（网络、一致性、排障）是真实的

### 2. 治理体系五件套

1. **注册与发现**：Nacos/Consul/Eureka 类，注意健康检查与推送一致性
2. **配置中心**：配置与代码分离、灰度发布配置、审计
3. **限流熔断**：保护下游（熔断）与保护自己（限流）是两件事
4. **负载均衡**：客户端负载均衡的坑（缓存的连接列表）
5. **全链路追踪**：没有 Trace 的微服务体系等于盲飞

### 3. Dubbo / Spring Cloud / Mesh 的选择

- Dubbo：RPC 性能强、Java 生态，接口治理精细
- Spring Cloud：HTTP/REST 友好、生态广、上手快
- Service Mesh（Istio 类）：治理能力下沉到 Sidecar，语言中立——代价是复杂度与延迟
- 实践观点：中小规模用框架级方案足够；Mesh 解决的是"多语言 + 强治理 + 大团队"问题

### 4. 微服务与 K8s 的关系

- K8s Service/Ingress 解决"网络可达"，治理框架解决"治理语义"
- 两条路线的融合与取舍（框架下沉 vs 平台上浮）

### 5. 常见反模式

- 分布式单体：拆了服务没拆数据
- 同步调用链过长：一次请求跨 8 个服务，延迟与可用性双输
- 无契约变更：接口即合同，向后兼容是纪律
