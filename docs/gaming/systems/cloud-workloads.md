# 游戏业务系统与云需求地图

> 面向游戏行业云解决方案设计。先把玩法与业务路径转换为状态、负载和服务目标，再讨论计算、存储、网络及运行方案；本文不提供未经压测的资源配比。

## 从业务形态识别系统边界

单人离线作品可能主要需要分发、云存档和数据服务；实时对战需要考虑匹配、会话与同步；持续世界需要进一步处理长期状态、区域和社交关系。不能把一张“游戏通用架构图”直接当成所有项目的部署方案。

**权威状态**由指定的可信节点裁决。Godot 多人网络资料展示了联网调用、节点权限和同步等机制，但使用网络框架并不会自动完成业务授权或防作弊设计。[Godot 多人网络](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)

| 业务系统 | 状态与负载特点 | 重点服务目标 | 可讨论的云能力 |
| --- | --- | --- | --- |
| 登录、账号与入口 | 身份、会话、突发登录 | 登录成功率、延迟、身份与权限 | 计算、入口治理、身份与安全 |
| 大厅、好友、公会与背包 | 持久化关系、查询及状态变更 | 正确性、数据可恢复、响应时间 | 数据库、缓存、消息与业务服务 |
| 匹配与房间 | 排队、地区、技能与组队约束 | 等待时间、匹配质量、分配成功率 | 调度、队列、缓存与容量管理 |
| 战斗或世界进程 | 活跃会话、模拟与同步状态 | 模拟耗时、网络质量、对局完成 | 合适的计算资源、网络和会话编排 |
| 支付、订单与发货 | 外部交易及资产账目 | 无重复发放、可追踪、可对账 | 事务、幂等、消息、审计 |
| 聊天与玩家内容 | 消息、关系、内容和治理 | 到达、延迟、滥用处理与申诉 | 实时通信、存储、审核及检索 |
| 更新与资源分发 | 大文件、地域差异、发布峰值 | 下载完成率、耗时、源站负载 | 对象存储、CDN、缓存及校验 |
| 埋点与分析 | 批流数据、延迟和数据质量 | 完整性、时效、查询与成本 | 数据管道、仓库、湖与分析引擎 |
| 研发与内容生产 | 源资产、构建、批处理、协作 | 任务等待、可复现与交付质量 | 存储、构建算力、GPU 与权限治理 |

云游戏把渲染结果通过流媒体交给终端，需求还涉及编码、端到端交互时延和每会话 GPU 资源。它与“使用云服务器承载普通游戏后端”是不同工作负载。

## 弹性策略取决于状态怎样结束

~~~mermaid
flowchart TD
  A["识别请求、任务或游戏会话"] --> B{"实例上是否持有活跃业务状态"}
  B -->|否| C["按容量与依赖约束调整副本"]
  B -->|是| D{"状态能安全迁移或恢复吗"}
  D -->|是| E["先验证迁移与恢复，再调整资源"]
  D -->|否| F["停止接入新会话，等待已有会话结束"]
  C --> G["验证玩家路径与成本"]
  E --> G
  F --> G
~~~

无状态接口也可能受数据库连接数、外部限流或缓存影响，不能无限扩容。持有对局的进程则需要停止接新会话、排空、结算和退出协议；直接按 CPU 阈值缩容可能中断玩家对局。

容量调研至少记录同时在线、房间数、每房间玩家与实体数、模拟频率、地图差异、网络消息、存储访问和突发持续时间。负载发生器应尽可能覆盖代表性行为组合，不能只用登录请求压测推断战斗容量。

## 支付成功、发货与持久化要分别验证

Steam 微交易文档将服务端完成交易与物品发放衔接起来。自己的业务仍需处理响应未知、重复通知、退款和对账。[Steam 微交易](https://partner.steamgames.com/doc/features/microtransactions/implementation)

建议通过订单和发放的唯一标识追踪状态，明确哪个记录是最终依据。支付页面返回成功、消息投递成功和背包到账是不同事实。发生异常时，要能找到缺口并受控补发，而不是不断重试所有步骤。

## 分发与实时交互需要分别测量

阿里云中国站的 CDN 下载文档说明了对象存储源站、缓存及预热在下载场景中的作用。这里仅将其作为文件分发实例，不据此推断所有地域、协议或实时战斗链路的能力。[文件下载加速及成本优化](https://help.aliyun.com/zh/cdn/use-cases/fdaaco)

更新包分发关注文件大小、缓存命中、下载失败和回源；实时玩法还要关注端到端延迟、抖动、丢包、运营商路径和玩家地域。应在目标地区和网络中观测，避免用机房间测速替代玩家实际体验。

## 将运行目标和成本放在同一验收表

| 场景 | 验收证据 | 成本分母示例 |
| --- | --- | --- |
| 开服与活动峰值 | 登录到进入玩法的成功率与排队 | 成功服务的玩家时长 |
| 实时对局 | 代表负载下的对局完成和时延分布 | 成功完成的对局数 |
| 内容分发 | 目标地区下载完成与失败重试 | 成功分发量或完成更新人数 |
| 构建平台 | 等待、构建、重跑及可用制品 | 通过验收的构建数 |
| 数据分析 | 延迟、完整性、查询和对账 | 有明确范围的数据处理量 |

以上是指标设计建议。分母、资源归属和统计周期应先一致，再比较方案。故障恢复还需验证存档、交易与进度，不只验证实例重新启动。
