# 策划岗位、需求与核心交付物

> 面向需要读懂策划需求的技术读者。本文把体验目标转成规则、配置、资源需求与验收证据，示例均为虚构设计。

## 策划连接体验意图与可执行规则

**游戏设计文档（GDD）** 承载设计目标和规则，但具体项目可能用文档、表格、编辑器配置与原型共同表达。策划的成果不能只按文档页数衡量；核心问题是不同团队能否根据同一份定义实现和验证同一种行为。

ScreenSkills 将主设计师与游戏体验、设计沟通联系起来。中文语境中的“主策、系统、数值、战斗”等拆分需要按项目核对，不宜把英文职位名称机械一一对应。[主设计师岗位资料](https://www.screenskills.com/job-profiles/browse/games/design/lead-games-designer/)

| 设计职责 | 应明确的内容 | 典型交付物 |
| --- | --- | --- |
| 主策与总体设计 | 核心体验、目标用户、系统依赖和取舍 | 设计原则、系统关系图、评审结论 |
| 系统策划 | 入口、状态、条件、操作、异常和反馈 | 规则文档、状态图、界面交互和配置字段 |
| 数值策划 | 成长节奏、产出消耗、战斗与奖励参数 | 数值模型、配置表、模拟条件和调参记录 |
| 关卡与战斗策划 | 场景目标、路径、节奏、技能及对抗关系 | 可玩原型、关卡配置、技能和敌人定义 |
| 文案与叙事设计 | 设定、人物关系、对白上下文与分支 | 文本及唯一标识、上下文、音频需求 |

## 一份需求至少要能回答哪些问题

建议用以下结构描述一个功能，而不是立即列技术组件：

1. **目标与边界**：为哪类玩家解决什么体验问题，哪些行为不在本次范围。
2. **进入条件**：角色、账号、区服、等级、时间、队伍等条件从哪里取得。
3. **状态与规则**：哪些操作有效，重复、超时、退出或掉线怎样处理。
4. **内容与配置**：需要哪些美术、音频、文案、表格及资源版本。
5. **数据与观察**：怎样知道玩家看见、进入、完成或放弃了功能。
6. **验收与运行**：谁确认体验，谁验证正确性，上线后谁调整和关闭。

## 示例：把“合作副本奖励”写到可验收

设想一个虚构功能：玩家组队完成限时副本后领取一次奖励。讨论至少应落到下面这些边界，实际规则由项目决定。

| 问题 | 需要形成的决定 | 验收样例 |
| --- | --- | --- |
| 哪个时区判定活动有效 | 服务端时间、开始和结束边界 | 开始前、边界时刻和结束后各验证 |
| 领奖次数怎样计算 | 按账号、角色还是副本结算记录 | 同账号多角色、重复请求分别测试 |
| 何时认定通关 | 权威结算和有效参与条件 | 中途退出、掉线重连、结算超时 |
| 奖励版本以什么为准 | 按进入、结算或领取时刻固定版本 | 进行中切换配置时结果可解释 |
| 背包满或发货失败怎样处理 | 暂存、邮件或重试的明确规则 | 失败后重试不会丢失或重复到账 |
| 如何解释客服争议 | 保留必要的参与、结算、发放证据 | 可按业务标识重建一次领奖过程 |

## 配置也是影响生产行为的变更

数值表可能改变价格、奖励和成长速度，文案可能改变玩家理解，资源引用可能造成缺失。配置应记录字段含义、单位、默认值、合法范围、依赖版本、审批与发布记录。

Unity Economy 将配置编辑和发布区分开，并提醒配置错误可能破坏游戏经济。这是某产品的具体机制；项目自身还需要确认缓存、新旧客户端及跨区服发布时的行为。[Economy 配置发布](https://docs.unity.com/en-us/Economy/publication)

评审建议同时保留“当前生效配置”和“拟发布配置”的差异。回退前要确认新配置是否已经产生不可直接撤回的奖励、交易或排名结果。关闭功能、停止新发放、补偿和修复数据是不同动作。

## 云与 AI 的切入点及常见误区

可讨论的方向包括需求检索、规则一致性检查、配置校验、测试草案和文案上下文整理。验收应检查遗漏是否减少、规则冲突是否被发现、人工复核总工时是否下降。AI 生成的数值或规则不能仅因表达流畅就视为已经平衡。

常见返工来自只描述正常路径、没有指定权威状态、表格字段没有单位，以及美术和音频需求晚于开发排期。架构师应先看这些交接缺口，再判断是否需要新的工具或平台。
