# 玩法、成长与游戏经济系统

> 面向希望理解“玩法为什么会形成系统需求”的读者。本文提供产品分析框架，不预设某类玩法必然提高留存或收入。

## 从玩家行动理解核心循环

**核心循环**是玩家反复经历的行动、反馈和下一步选择；**成长系统**把多个循环连接成能力、内容或目标的变化。例如虚构的合作探险游戏中，组队探索、完成挑战、取得资源、调整装备再参与新挑战，可以作为待验证的循环。

循环只是设计假设。玩家可能享受合作，却不愿重复收集；也可能已经理解规则，但设备性能或匹配等待让其离开。因此，应把体验反馈和系统质量一起观察，不能把所有流失都归因于“奖励不够”。

| 设计层次 | 需要弄清的机制 | 对业务与技术的影响 |
| --- | --- | --- |
| 即时玩法 | 操作、反馈、胜负和难度 | 响应时间、同步、规则裁决 |
| 成长与内容解锁 | 经验、装备、技能、任务及进度 | 状态保存、配置版本和旧数据兼容 |
| 社交与协作 | 队伍、公会、好友、竞争及交易 | 关系、匹配、聊天、分区与治理 |
| 赛季与长期目标 | 周期、排名、奖励、重置和继承 | 结算、快照、跨版本与解释口径 |
| 商业化 | 购买的权益与体验关系 | 商品、支付、到账、退款和支持 |

## 游戏经济是资源的产出、转移与消耗

**资源来源（Source）** 指资源怎样进入玩家持有量；**消耗出口（Sink）** 指资源怎样离开；**转移**改变持有人，但不一定改变全体玩家总量。货币、道具、体力和次数可能有不同的上限、有效期和交易规则。

Unity Economy 将货币、库存物品、虚拟购买和真实货币购买作为不同资源类型。这里仅借用其帮助区分业务对象，具体项目不必采用该产品。[Economy 资源分类](https://docs.unity.com/en-us/economy/item-types)

对同一对象、同一统计范围，可用以下恒等关系检查账目：

~~~text
期末持有量
= 期初持有量 + 产出 + 转入 - 消耗 - 转出 - 过期 + 明确记录的调整
~~~

这个关系不证明经济平衡，只帮助发现漏记和异常。分析还需要按玩家阶段分组，查看资源分布、交易速度和实际用途；平均持有量可能掩盖新玩家不足与老玩家积压同时存在。

## 用一次奖励调整说明系统联动

假设运营准备增加活动奖励，不能只修改产出表。还要确认奖励能否交易、是否替代其他资源、是否改变排名、是否挤占付费权益，以及活动结束后剩余资源如何处理。

~~~mermaid
flowchart TD
  A["提出奖励或成长调整"] --> B["列出产出、消耗、交易与权益依赖"]
  B --> C{"是否改变不可直接撤回的玩家资产"}
  C -->|是| D["准备版本记录、补偿与对账方案"]
  C -->|否| E["准备配置切换与观察方案"]
  D --> F["在约定样本中验证规则和体验"]
  E --> F
  F --> G{"达到目标且未突破约束吗"}
  G -->|否| H["停止扩大并复核设计"]
  G -->|是| I["按受控范围发布并跟踪长期影响"]
~~~

建议在变更单中写明：作用群体、资源标识、预期行为、观测窗口、异常判定及责任人。若结果有延迟，短期参与增加只能证明某个阶段变化，不能直接证明长期留存或经营改善。

## 不同品类需要不同的观察重点

| 业务形态 | 可优先观察的事情 | 不宜直接沿用的假设 |
| --- | --- | --- |
| 单人叙事或买断作品 | 内容体验、完成路径、存档兼容和追加内容 | 必须以每日登录为主要目标 |
| 实时竞技 | 公平性、匹配质量、对局响应和规则可信 | 提升服务器数量即可改善所有体验 |
| 策略与长期经营 | 成长、联盟、资源流动、赛季或区服生态 | 全体用户平均值代表所有阶段 |
| 休闲与广告变现 | 单局节奏、广告触点、回访及设备体验 | 广告展示越多整体收益越好 |
| 用户创作内容 | 创作、审核、发现、反馈及创作者激励 | 内容增长不需要治理与分发机制 |

表格是调研方向，各类产品可以混合。具体结论需要结合玩法、地区、群组和实验结果。

## 架构与 AI 的边界

关键经济状态应有明确的可信来源、访问权限和审计记录；重复请求不能重复发放，同一物品的业务标识不应因本地化名称改变。存储、消息和缓存的选择应服务这些业务不变量。

AI 可以辅助整理规则、发现配置冲突和构造测试情形。将生成模型接入对话角色时，要区分“说出奖励承诺”和“实际变更资产”：对资产的操作必须经过确定的规则校验。策划仍需为体验目标和经济结果负责。
