# 游戏核心指标与统计口径

> 面向使用游戏数据进行业务沟通的读者。本文先约定用户、时间与收入范围，再解释指标及其局限；不提供缺乏适用条件的行业达标线。

## 先签订一份“指标契约”

每个指标至少记录：业务问题、定义、计算公式、时间与时区、用户去重标识、收入范围、过滤规则、数据来源、更新延迟、负责人和定义版本。账号、设备、角色、安装不是同一个单位。

Unity Analytics 的不同页面展示了按日活跃、留存和收入分析的方式，也存在不同收入范围。例如仪表盘中的 IAP 收入与 Data Explorer 中可能包含广告事件的指标不能只按同名直接合并。[Unity 仪表盘](https://docs.unity.com/en-us/analytics/dashboards/dashboards) · [Data Explorer 指标](https://docs.unity.com/en-us/analytics/data-explorer/data-explorer-v1)

## 活跃、并发和留存

| 指标 | 本文采用的定义或必要约定 | 常见误解 |
| --- | --- | --- |
| DAU / WAU / MAU | 日、周、月窗口内发生约定有效行为的去重用户数；窗口需说明自然或滚动 | MAU 等于每天 DAU 相加 |
| CCU / PCU | 同时在线用户数 / 给定期间的峰值同时在线数；需定义在线状态和采样间隔 | 可直接由 DAU 用固定倍数推算 |
| 新增用户 | 首次满足约定条件的用户，明确是安装、启动、注册还是进入玩法 | 重装、跨端、换设备必然是新人 |
| 第 N 日留存 | 同一新增群组在第 N 日活跃的人数 / 该群组初始人数 | 等于第 N 日及之后任一天回访 |
| 会话时长 | 按会话开始、结束和超时规则计算 | 后台挂起时间都是有效游戏时长 |
| 漏斗转化 | 完成下一步的合格用户 / 满足上一步条件的用户 | 不同人群和时间窗口可直接相除 |

**群组（Cohort）** 指按共同条件划定的一组用户，例如同日首次启动且来自同一投放地区的人。本文将新增当天记为 D0，D1 为次日，按同一约定时区的自然日计算。其他系统可能采用滚动 24 小时窗口或不同命名，比较前必须统一。

若某日新增 1,000 名用户，次日其中 300 名活跃，则该群组 D1 留存为 30%。若 D7 尚未到来，该群组 D7 应标记未成熟，不能填零或当成已观测结果。以上均为虚构算例。

## 付费、广告与获客回收

令同一时间窗口内活跃用户数为 U、内购付费用户数为 P、按约定统计的内购金额为 R。分母非零时：

~~~text
内购付费率 = P / U
内购 ARPU = R / U
内购 ARPPU = R / P
内购 ARPU = 内购付费率 × 内购 ARPPU
~~~

**ARPU**是每用户平均收入，**ARPPU**是每付费用户平均收入。上式成立依赖相同时间、用户与金额口径。若 ARPU 加入广告收入而 ARPPU 只含内购，不能继续使用该分解。

| 指标 | 计算与解释 | 必须补充的口径 |
| --- | --- | --- |
| ARPDAU | 一天的约定收入 / 当天 DAU | 仅内购、仅广告或合计；毛额或净额 |
| 广告 eCPM | 广告收益 / 广告展示次数 × 1,000 | 收益预估或结算值、展示定义、币种 |
| CPI | 归属某投放范围的费用 / 归因安装数 | 有效安装、重装、归因规则及窗口 |
| 第 N 日累计 ROAS | 获客群组截至第 N 日的累计归因收入 / 对应广告费用 | D0 是否计入、收入范围、税费退款 |
| 已观测 LTV | 群组在明确窗口内的累计约定价值 / 群组初始人数 | 收入还是贡献利润、窗口长度 |
| 预测 LTV | 用模型估计更长期的每用户价值 | 假设、训练群组、误差和预测跨度 |
| 回收期 | 累计回收达到约定投入的时间 | 只覆盖投放费还是包含其他成本 |

**ROAS**是广告支出回报的比值，不是利润率；**LTV**是用户生命周期价值，但实际看板常只展示有限窗口的观测值。应把“D30 观测收入 LTV”和“预测全年贡献 LTV”写成不同指标。

虚构算例：某批投放花费 10,000 元，带来 1,000 次符合口径的归因安装；截至 D7 累计产生 6,000 元归因内购毛额。则 CPI 为 10 元，D7 累计毛额 ROAS 为 60%，D7 已观测内购毛额 LTV 为 6 元。这里没有扣除退款、平台费用、服务成本等，不能据此声称利润或最终回收。

## 从看板变化走到业务解释

~~~mermaid
flowchart TD
  A["观察到指标变化"] --> B{"定义、埋点和数据完整性一致吗"}
  B -->|否| C["修复口径或数据问题"]
  B -->|是| D["按版本、来源、地区和用户阶段拆分"]
  D --> E{"群组已经成熟且可比较吗"}
  E -->|否| F["补足窗口或调整比较对象"]
  E -->|是| G["提出原因假设并检查干扰因素"]
  G --> H["用实验、访谈和服务证据验证"]
  H --> I["记录结论及适用边界"]
~~~

留存下降可能来自流量结构变化、玩法、服务故障或埋点变化。收入上升也可能来自短期促销或少数用户。只比较总量容易把群组构成变化误认为产品改进。

埋点应说明触发条件、字段、业务唯一标识、发生时间与接收时间、去重及版本。对购买、到账等关键事件，应与权威业务记录对账，避免客户端重复上报造成虚增。

## 指标如何帮助云与 AI 方案验收

可把成功对局、合格资产、已解决工单等作为有业务意义的产出，再定义对应单位成本。必须保留容量、质量和服务目标：便宜但无法完成对局的资源，不是有效成本优化。

Steam UTM 文档说明某些跨浏览器和跨应用路径不能可靠关联。因此，归因不完整和数据缺失应被记录，不能通过任意放大系数“补成真实值”。同样，AI 效率评估也需要保留失败、返工和人工复核成本。[Steam UTM 边界](https://partner.steamgames.com/doc/marketing/utm_analytics)
