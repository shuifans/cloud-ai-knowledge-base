# 面向不同岗位的业务调研

> 面向游戏行业云与 AI 解决方案调研。本文是一套可调整的问题框架，帮助把模糊诉求转成具体工作、验证证据和责任分工，不预设任何客户的现状。

## 用最近一次工作还原真实流程

相比问“是否需要 AI”，可以请业务方描述最近一次版本发布、资产交付或活动异常：谁提出，交给谁，经过哪些工具，哪里等待，什么才算完成。获得授权后查看必要的脱敏样例，往往比抽象需求列表更有帮助。

建议记录六类信息：项目和阶段、角色与责任、输入和交付物、工作频率与规模、质量与时间要求、当前失败和返工。未知项保持为未知，不用演示中的理想流程填补。

## 按岗位组织问题与材料

| 对象 | 主要问题 | 可请求的必要脱敏材料 | 可形成的验收方向 |
| --- | --- | --- | --- |
| 制作人、PM | 哪个阶段目标受到影响？最难控制的依赖是什么？ | 里程碑、风险、变更和交接清单 | 阻塞、交付偏差与风险控制 |
| 策划 | 规则如何到达程序与测试？哪里最常出现理解差异？ | 一份规则、配置字段和验收样例 | 完整性、冲突、返工 |
| 主美、TA | 一份合格资产如何入库？失败通常发生在哪一步？ | 需求、规范、源文件目录与失败记录 | 合格交付、修改、集成和运行表现 |
| 客户端、引擎与工具 | 是编译、加载、设备性能还是资源协作限制效率？ | 脱敏构建与性能记录 | 可用制品周期、设备表现 |
| 服务端、运维与安全 | 峰值来自哪里？状态怎样保存和恢复？ | 系统边界、负载、故障与成本分类 | 玩家路径、恢复与容量证据 |
| 发行、投放 | 素材如何迭代？用户和收入怎样归因？ | 素材标签、群组定义和报表口径 | 有效素材、用户质量与回收 |
| 运营、数据 | 活动目标是什么？怎样判断不是流量结构造成的变化？ | 活动方案、指标契约、群组数据 | 可解释效果与长期影响 |
| 客服、社区 | 哪类问题重复最多？哪些必须转人工？ | 脱敏工单、知识版本和升级规则 | 解决、重开、知识质量和授权 |
| 财务、采购及法务 | 谁承担持续费用和维护？哪些约束必须满足？ | 费用口径、采购与验收责任 | 可持续投入、权利与责任边界 |

岗位分工本身也要核对。公开岗位资料只提供参考，不证明目标公司的组织结构。[ScreenSkills 岗位体系](https://www.screenskills.com/job-profiles/browse/games/)

## 把“痛点”转成可以证伪的假设

以虚构的“美术效率低”为例，至少可能对应创作探索慢、规格反复变化、审批等待、外包返工、导入失败或工具排队。不同原因需要不同干预，不能直接归结为缺少生成模型。

~~~mermaid
flowchart TD
  A["收集业务诉求"] --> B["观察具体工作与交接"]
  B --> C["核对频率、耗时、失败与结果"]
  C --> D{"有可复核的瓶颈证据吗"}
  D -->|否| E["补采样例与测量"]
  E --> B
  D -->|是| F["形成干预假设和备选办法"]
  F --> G["约定质量、成本与停止条件"]
  G --> H["验证后决定采用、调整或停止"]
~~~

可以将假设写成：“在给定风格与设备要求下，减少资产导入错误，会降低每份合格资产的总返工工时；通过同类任务比较验证。”它明确了条件、干预和观察对象，也允许结果证明假设不成立。

## 一页场景记录应包括什么

| 字段 | 记录要求 |
| --- | --- |
| 背景与范围 | 产品形态、阶段、市场、岗位及本次边界 |
| 当前流程 | 输入、操作、交接物、系统与运行责任 |
| 已知事实 | 来源、观察时间、测量口径和置信边界 |
| 待验证假设 | 可能原因、需要什么证据、由谁补齐 |
| 候选办法 | 流程调整、现有工具改进与技术方案的代价 |
| 验证设计 | 样本、基线、质量标准、窗口和失败判定 |
| 投入与结果 | 集成、使用、人工复核、维护与预期产出 |
| 责任与退出 | 决策、预算、验收、运行、停止和回退 |

不要把“支持者认为不错”填成验收完成，也不要把样例实验的结果扩展成全公司收益。**概念验证（PoC）** 只能证明其范围内的问题；进入生产还需要接口、权限、运行和持续费用等证据。

## 知识沉淀如何保持可复用

每次新增记录时，把来源事实、分析判断和待验证经验分开。公开文章只使用可公开信息与泛化场景；个人经验进入知识库前，先去掉可识别项目与未公开数据，再保留可复用的机制和条件。

复盘应回答原假设是否成立、哪些条件改变、什么方案被采用、哪些问题仍未解决。只有证据允许时才记录收益，未执行的方案保留为设计示例。
