# 游戏公司的组织、岗位与协作

> 面向与游戏团队沟通的架构师。读完可以从职责、交付物和协作关系找到需要参与讨论的人，而不只记住岗位名称。

## 项目责任与职能能力形成两条线

**项目组**围绕某款游戏的交付和经营组织工作；**职能团队**围绕美术、研发、数据等专业能力组织人员；**共享平台**可能为多个项目提供账号、支付、运维或研发工具。实际组织可能混合这三种方式。

小团队可能一人兼任策划、开发与运营，大团队则可能把同一工作拆成多个岗位。ScreenSkills 的岗位资料也区分工作室规模带来的分工差异。因此，下面的中文岗位表是供访谈使用的职责拆分，不是任何公司的固定组织图。

## 岗位要连到交付物和协作方

| 职责或岗位 | 日常工作与主要交付 | 主要协作方 | 可讨论的评价维度 |
| --- | --- | --- | --- |
| 制作人、项目负责人 | 产品方向、范围取舍、里程碑和资源安排 | 核心主创、发行、管理层 | 阶段目标、质量、预算和风险 |
| 项目经理（PM） | 排期、依赖、进度、变更与问题跟踪 | 各专业负责人 | 阻塞时间、承诺偏差、问题闭环 |
| 主策划 | 体验目标、系统关系、设计评审 | 制作人、主程、主美 | 体验一致性、可实现性 |
| 系统策划 | 功能规则、状态、交互与配置需求 | 程序、UI、测试、运营 | 规则完整性、边界和验收 |
| 数值策划 | 成长、战斗参数、产消和奖励配置 | 系统策划、数据、运营 | 平衡、经济稳定性、可解释性 |
| 关卡与战斗策划 | 节奏、空间、敌人、技能及可玩样例 | 客户端、美术、音频 | 可玩性、可读性、调试效率 |
| 文案与叙事设计 | 世界观、人物、对白和叙事规则 | 设计、美术、本地化 | 一致性、上下文完整性 |
| 主美与艺术负责人 | 风格基准、资产规范、视觉评审 | 制作人、各美术组、TA | 风格一致性、返工与交付质量 |
| 原画、角色、场景、动画、特效 | 按专业制作源文件和引擎资源 | 策划、TA、集成与测试 | 合格交付、修改工时、运行效果 |
| UI/UX | 界面结构、交互原型、视觉与可用性 | 策划、客户端、用户研究 | 理解成本、完成率、可访问性 |
| 技术美术（TA） | 工具、资源规范、着色与性能协作 | 美术、引擎及客户端 | 工具稳定性、集成与性能问题 |
| 音频、作曲、配音及音频集成 | 音效、音乐、对白与触发配置 | 叙事、设计、客户端 | 表现质量、音量规范、触发正确性 |
| 主程、技术负责人 | 技术路线、接口与系统质量要求 | 制作人、各研发组 | 技术风险、交付和维护成本 |
| 客户端、引擎与图形程序 | 交互、表现、资源加载、平台适配 | 策划、美术、服务端 | 帧时间、崩溃、内存和兼容性 |
| 服务端程序 | 权威状态、业务规则、持久化和接口 | 客户端、运维、测试 | 正确性、延迟、容量与恢复 |
| 工具与构建工程 | 编辑工具、导入、编译打包、制品管理 | 全体内容生产与研发团队 | 等待时间、可复现性、失败定位 |
| QA 与测试开发 | 风险分析、用例、缺陷和自动化 | 开发、策划、发行 | 缺陷影响、回归证据、复现质量 |
| 运维、SRE 与平台工程 | 容量、监控、发布、恢复和资源治理 | 服务端、运营、安全 | 玩家服务目标、恢复和资源效率 |
| 发行、商务与渠道 | 市场计划、合作条款、渠道接入 | 研发、法务、运营 | 市场目标、接入与履约 |
| 投放与素材创意 | 广告计划、素材实验、预算与归因 | 美术、数据、发行 | 获客群组质量、成本和回收 |
| 产品与活动运营 | 版本节奏、活动规则、用户分层 | 策划、数据、客服、研发 | 活跃、体验、收入与长期影响 |
| 社区、客服与舆情 | 内容沟通、工单、问题升级和反馈 | 运营、研发、安全 | 解决率、重开率、反馈闭环 |
| 数据与用户研究 | 埋点、指标、实验、访谈与分析 | 业务各团队 | 数据可信度、结论适用范围 |
| 安全、法务、采购与财务 | 风险审查、合同、采购及成本口径 | 项目和业务负责人 | 控制有效性、责任和可追溯性 |

表中的“评价维度”用于理解工作结果，不是绩效考核标准。例如缺陷数量不能直接评价测试能力；降低工单数量也可能来自入口难找，而非玩家问题减少。

## 从一项变更找出真正的协作关系

以虚构的“新增限时合作副本”为例，策划提出玩法与奖励，客户端和服务端共同确定实现，TA 与美术确认资源预算，QA 覆盖边界，运营安排活动，客服准备解释口径。具体责任必须在项目内确认。

~~~mermaid
flowchart TD
  A["确定变更目标和验收结果"] --> B["识别提出者、使用者、实现者"]
  B --> C{"涉及共享系统或跨团队数据吗"}
  C -->|是| D["加入平台、数据及相应责任方"]
  C -->|否| E["由项目内职责完成评审"]
  D --> F["指定最终决策人与交接物"]
  E --> F
  F --> G{"验收证据和运行责任齐备吗"}
  G -->|否| B
  G -->|是| H["进入排期与执行"]
~~~

可以借用责任矩阵的思想，为每个交付物记录“执行、最终决策、提供意见、需要知情”的角色。岗位表解决“有哪些人”，责任矩阵解决“这件事谁负责”。矩阵应围绕具体事项编写，避免同一事项没有最终决策者或多人彼此等待。

## 架构师需要同时找到四类责任

**业务责任人**定义结果，**使用团队**描述真实工作，**技术与运行责任人**说明接口及长期维护，**预算与采购责任人**确认投入范围。四种责任可能由同一人承担，也可能跨项目组、共享平台和发行方。

| 讨论对象 | 有用的问题 | 希望取得的材料 |
| --- | --- | --- |
| 制作人与 PM | 哪个里程碑受影响？最常阻塞在哪个交接点？ | 里程碑、依赖和风险记录 |
| 策划与美术 | 什么才算合格交付？最近一次返工原因是什么？ | 脱敏需求、风格标准、验收样例 |
| 研发与平台 | 谁拥有状态？哪些错误不能仅靠重试解决？ | 系统边界、接口和恢复流程 |
| 发行与运营 | 用哪个用户群、什么窗口判断改善？ | 指标定义、活动及归因规则 |
| 采购与管理 | 谁承担新增维护工作？持续费用归哪个项目？ | 责任分工、预算口径和验收流程 |

常见问题包括把制作人与 PM 的职责视为完全相同、把 TA 当成通用美术外包岗位、把游戏运营等同于服务器运维，以及只听技术负责人而没有观察实际使用者的工作。解决办法是用最近一次真实工作交接核对岗位描述。
