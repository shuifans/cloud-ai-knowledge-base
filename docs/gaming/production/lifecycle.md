# 游戏从立项到停运的生命周期

> 面向需要判断游戏项目当前阶段和下一步需求的读者。本文按“阶段要消除什么不确定性”组织生命周期，而不预设开发周期、团队人数或成功率。

## 阶段名称背后是不同的验证目标

**原型（Prototype）** 用于快速验证特定假设；**垂直切片（Vertical Slice）** 通常指覆盖一段代表性体验与制作环节的样例，实际验收范围需由项目定义。它可以帮助验证制作方式，却不意味着团队已经能按同样效率批量生产全部内容。

育碧公开流程包含概念、预制作、制作与运营等阶段，其预制作强调工具和流程准备。这里将其作为阶段划分的实例；项目自己的 Alpha、Beta 或“首测”必须另写验收定义，名称相同不代表完成程度相同。[育碧制作流程](https://www.ubisoft.com/en-us/company/how-we-make-games/creative-process)

| 阶段 | 需要回答的问题 | 建议形成的证据 | 主要协作角色 |
| --- | --- | --- | --- |
| 机会与立项 | 面向谁，体验与市场假设是什么 | 用户假设、产品定位、投入范围与关键风险 | 制作人、策划、发行、管理层 |
| 概念与原型 | 核心交互是否值得继续 | 可玩样例、观察记录、失败和修改理由 | 策划、程序、美术、用户研究 |
| 预制作 | 内容与系统能否按计划生产 | 代表性样例、工具链、规范、成本假设 | 各专业负责人、PM、QA |
| 量产与集成 | 团队能否稳定交付完整内容 | 内容清单、版本制品、依赖和质量记录 | 全体研发与内容团队 |
| 测试与市场验证 | 功能、体验、设备与服务是否达到目标 | 缺陷、性能、用户研究与指标口径 | QA、研发、发行、数据 |
| 上线准备 | 交付、推广、玩家服务能否共同就绪 | 发布清单、容量证据、值守与异常预案 | 研发、运维、发行、客服 |
| 持续运营 | 新内容和运行服务能否兑现承诺 | 版本与活动效果、成本和服务质量 | 运营、研发、数据、玩家服务 |
| 有序退出 | 玩家权益、数据和依赖怎样结束 | 通知与处理记录、数据处置、系统退出清单 | 业务负责人、法务、客服、技术 |

## 阶段关口不是只检查“做了多少”

进度清单描述完成量，关口评审决定能否继续投入。例如原型好玩但生产规范未形成，可以继续验证，不能直接据此承诺大规模量产成本。反过来，按时完成全部功能也不能代替玩家体验验证。

~~~mermaid
flowchart TD
  A["定义本阶段假设、投入和停止条件"] --> B["制作与收集证据"]
  B --> C{"关键假设是否成立"}
  C -->|证据不足| D["缩小实验或补充验证"]
  D --> B
  C -->|不成立| E["调整方向或终止本阶段投入"]
  C -->|成立| F{"下一阶段的资源与责任齐备吗"}
  F -->|否| G["补齐依赖与计划"]
  G --> F
  F -->|是| H["进入下一阶段并持续复核"]
~~~

建议每次评审记录假设、证据、尚未验证的部分、决策者和复核触发条件。应把“可以发布测试版本”和“适合扩大商业投放”作为不同决定。

## 测试标签要写清楚范围

“技术测试”可能只验证稳定性，“删档测试”描述进度保留方式，“付费测试”涉及交易与退款安排，“小范围市场测试”可能验证某地区用户行为。它们不是一套统一的线性阶梯。

比较测试数据前，需要知道进入测试的人如何招募、是否付费、内容开放到哪里、设备与地区分布、数据是否覆盖完整观察周期。核心玩家邀请测试的留存不能直接当成大众获客后的留存预测。

Steam 的发布流程将商店资料和游戏构建作为不同检查对象，二者都需要完成相关审核。这说明发布准备包含内容、平台和业务交付，不能只检查程序能否运行。[Steam 发布流程](https://partner.steamgames.com/doc/store/releasing?l=schinese)

## 上线与停运都需要跨团队交接

上线前建议共同演练登录、进入游戏、关键玩法、购买与到账、更新、工单升级。每条路径记录负责人和失败时的处理方式。流量计划、投放时间、值守和资源准备应能对齐到同一发布窗口。

进入退出阶段时，应先盘点充值、虚拟权益、订阅、账号、社区、合同及存储依赖，再由相关责任方确定适用的通知、权益处理和数据保留要求。停掉计算资源不代表服务责任已经结束；单人作品的服务器退出也不必然等于离线游戏不可运行。

## 云与 AI 需求随阶段改变

原型阶段可先验证最小工作流，预制作阶段关注工具集成和资产规范，量产阶段分析编译与内容生产等待，上线阶段验证峰值容量与恢复，运营阶段连接业务效果和单位成本。退出阶段则需要确认归档、删除、依赖解除和账单停止。

避免在原型阶段以成熟游戏的规模假设采购资源，也避免在上线前才讨论账号、支付、数据和客服。技术方案的时间安排应对应具体关口，而不是只对应“游戏研发”这个大标签。
