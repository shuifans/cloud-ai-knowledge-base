# 版本研发、测试与发布流程

> 面向游戏项目交付、运行及方案负责人。本文把需求、客户端、服务端、资源和配置连接起来，说明版本如何进入玩家环境，以及异常时怎样止损。

## 一个业务版本可能包含多种制品

**客户端包**包含设备上运行的程序及部分资源；**服务端版本**承担在线逻辑；**资源包**承载内容；**配置**决定部分规则。一个“活动版本”可能同时涉及这些对象，它们的生效时间、分发方式和回退能力不同。

建议建立版本清单，记录各制品标识、来源提交、构建输入、依赖范围、生效区域、发布顺序和回退条件。测试包与线上包若不是同一可追溯制品，测试结论需要重新解释。

| 阶段 | 交付物与责任 | 放行前应看到的证据 |
| --- | --- | --- |
| 需求评审 | 策划与业务明确规则，研发和 QA 共同分析风险 | 正常、异常、权限和旧版本行为 |
| 排期与依赖 | PM 与各负责人确定范围和交接 | 资源、接口、渠道和数据依赖清单 |
| 开发与集成 | 各专业交付代码、资源和配置 | 审查、自动校验、集成制品 |
| 质量验证 | QA 组织，责任团队修复与复核 | 功能、设备、性能、存档及网络证据 |
| 发布准备 | 发布负责人协调运维、运营、客服 | 发布窗口、停止条件、值守、公告口径 |
| 渐进发布 | 按平台允许方式分阶段进入生产 | 关键路径与玩家影响观测 |
| 复盘 | 业务、研发与运行团队共同检查 | 结果、缺陷、恢复行动和后续责任 |

Steam 文档建议先在测试分支验证构建，再移至默认分支。这个机制适用于相应平台，移动渠道审核和其他分发体系需另行确认。[Steam 更新实践](https://partner.steamgames.com/doc/store/updates)

## 兼容矩阵比单独一个版本号更有用

| 组合 | 必须回答的问题 |
| --- | --- |
| 旧客户端与新服务端 | 接口字段、规则和资源缺失时怎样处理 |
| 新客户端与旧服务端 | 发布次序变化时能否安全启动 |
| 新配置与旧缓存 | 多个实例生效不一致时是否影响公平与结算 |
| 新资源与旧索引 | 缺失、下载中断、校验失败怎样反馈 |
| 新版本与旧存档 | 字段迁移、内容删除、回退是否可恢复 |
| 渠道包与平台 SDK | 登录、支付、权限和审核要求是否一致 |

**热更新**描述某种无需完整重新安装的变更路径，不代表可跳过平台规则、兼容验证或发布审批。配置也可能改变重大业务行为，Unity Economy 文档明确区分编辑与发布状态。[配置发布](https://docs.unity.com/en-us/Economy/publication)

## 游戏测试应保留业务上下文

除通用功能测试，还应考虑帧时间与卡顿、设备内存、弱网和重连、匹配等待、长时间运行、资源下载、支付到账、对局公平和经济漏洞。压测需要说明区服、地图、实体数量、行为组合和账号状态。

机器人可能适合生成某些负载，却未必复现真实玩家的探索、社交、交易与作弊路径。脚本请求数、在线连接数、成功进入对局数是不同的测量对象。

## 回退之前先判断数据后果

代码回退不会自动撤销已发放奖励、已完成交易或已经升级的存档。出现重复奖励时，优先停止进一步错误发放并保存证据，随后按照业务与权限约束决定修复或补偿。粗暴恢复整库可能覆盖正常玩家在故障期间的合法进度。

发布后的观察建议以玩家路径为中心：能否登录、进入玩法、完成结算、获取权益和继续游戏。服务进程存活不等于玩家路径成功。

## 技术改进先找实际等待与失败

云构建、资源缓存、制品管理、测试设备和 AI 缺陷归类都可能改善流程。先记录提交到可测试包的时间、排队和执行分别耗时、失败类别、重跑与返工，再选择改进点。把构建时间缩短但增加集成返工，未必改善版本交付。
